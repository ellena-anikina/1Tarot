# Этап 2. Проект интеграции Robokassa

Дата: 27 ноября 2026  
Основа: `01-audit.md`, документация Robokassa (`pay-interface`, `notifications-and-redirects`, `testing-mode`, `holding`, `refund-api`, `xml-interfaces`, `fiscalization`).  
Код на этом этапе не меняется.

## 1. Решения одним взглядом

| Вопрос | Решение |
| --- | --- |
| Режимы оплаты | `off`, `mock`, `robokassa` |
| Тестовый режим Robokassa | отдельный флаг `ROBOKASSA_TEST=1`, тестовые пароли |
| Номер заказа для Robokassa | числовой `InvId`, уникальный для каждой попытки |
| Номер заказа для посетителя | прежний текстовый `K7Q3-M9XP` |
| Привязка к раскладу | подписанный токен в `Shp_order` |
| Схема оплаты на запуске | одностадийная: деньги списываются сразу |
| Холдирование | позже, только если Robokassa разрешит самозанятому |
| Главное подтверждение | Result URL + серверная проверка |
| Резервное подтверждение | `OpStateExt` в боевом режиме |
| Подтверждение для теста | подписанный Success URL (только при `ROBOKASSA_TEST=1`) |
| Подтверждение для посетителя | HMAC-токен сайта, как сейчас |
| Хранение заказов | без базы, в памяти только кэш подтверждений |
| Возврат | Refund API Robokassa, JWT с паролем №3 |
| Чек | `Receipt` в запросе на оплату, настройка отключаемая |
| API-маршруты | 5 новых + 2 изменённых |

## 2. Режимы и настройки

### 2.1. `PAYMENTS_MODE`

| Значение | Поведение |
| --- | --- |
| `off` | все расклады бесплатны, оплата выключена |
| `mock` | тестовая страница `/oplata`, деньги не списываются |
| `robokassa` | настоящая или тестовая Robokassa по флагу `ROBOKASSA_TEST` |
| пусто | `mock` (как сейчас) |
| неизвестное | в разработке `mock`, в production `off` + громкая ошибка в журнале |

Почему так: опечатка не должна незаметно включать тестовую оплату на боевом сайте. Если режим сломан, лучше временно сделать всё бесплатным, чем показывать «оплачено» без денег.

### 2.2. Переменные окружения

```dotenv
# Режим
PAYMENTS_MODE=robokassa
PAYMENTS_SECRET=длинная-случайная-строка

# Магазин
ROBOKASSA_LOGIN=nezhnoetaroru
ROBOKASSA_TEST=1

# Тестовые пароли (из блока «Параметры проведения тестовых платежей»)
ROBOKASSA_TEST_PASSWORD1=
ROBOKASSA_TEST_PASSWORD2=

# Боевые пароли (из основного блока)
ROBOKASSA_PASSWORD1=
ROBOKASSA_PASSWORD2=
ROBOKASSA_PASSWORD3=

# Настройки, которые можно выключить без правки кода.
# Самозанятый: чек НПД формируют «Робочеки СМЗ», поэтому Receipt не передаём.
# Если поддержка скажет иначе — поставить 1, код уже готов к этому.
ROBOKASSA_RECEIPT=0
ROBOKASSA_REFUND_RECEIPT=0
ROBOKASSA_EXPIRATION=1
```

Правила:
- `PAYMENTS_SECRET` обязателен в production. Без него маршруты оплаты отвечают ошибкой, а не работают с запасным секретом.
- `ROBOKASSA_TEST` по умолчанию `1`. Боевые платежи включаются только явным `0`.
- Тестовые и боевые пароли лежат отдельно. При запуске не нужно переставлять значения — только поменять `ROBOKASSA_TEST`.
- Пароль №3 нужен только для возвратов; в тестовом режиме возврат имитируется.
- `ROBOKASSA_RECEIPT=0` — основной режим для самозанятого: чек НПД регистрирует сервис «Робочеки СМЗ». Передача чека в запросе остаётся запасным вариантом.

### 2.3. Проверка настроек при старте

При `PAYMENTS_MODE=robokassa` сервер проверяет:
- задан `ROBOKASSA_LOGIN`;
- задана нужная пара паролей (тестовая или боевая);
- в боевом режиме задан `PAYMENTS_SECRET`;
- `ROBOKASSA_TEST` равен `0` или `1`.

Если чего-то нет:
- в журнал пишется понятная ошибка;
- создание платежа отвечает 503 «Оплата временно недоступна»;
- уже оплаченные трактовки продолжают открываться по старым подтверждениям, если секрет на месте.

## 3. Модель заказа

### 3.1. Два номера

| Номер | Пример | Где виден | Зачем |
| --- | --- | --- | --- |
| `orderId` | `K7Q3-M9XP` | посетителю, в дневнике, в письмах | удобно продиктовать |
| `invId` | `179512345678901234` | Robokassa, журнал сервера, возврат | требует числовой формат |

`invId` — строка из цифр, а не `number`: так не теряется точность и не важно, что число большое.

Формат: миллисекунды времени + 6 случайных цифр. Уникален для каждой попытки оплаты, в том числе повторной.

### 3.2. Токен заказа

Внутри — только то, что нужно для проверки. Вопрос и карты целиком не хранятся, только отпечаток.

```ts
interface RobokassaOrder {
  v: 1;
  kind: "rk-order";
  id: string;          // K7Q3-M9XP
  inv: string;         // числовой InvId строкой
  spread: SpreadId;
  amount: number;      // целые рубли
  reading: string;     // отпечаток вопроса, темы и карт
  payBefore: number;   // до какого времени действует ссылка
  acceptUntil: number; // до какого времени принимаем уведомление
  test: 0 | 1;         // тестовый или боевой
}
```

Сроки:
- `payBefore` — 1 час, как сейчас;
- `acceptUntil` — 7 дней: уведомление может прийти позже, чем закончилась ссылка;
- подтверждение оплаты — 30 дней с момента платежа.

Подпись:
1. JSON → base64url.
2. HMAC-SHA256 с `PAYMENTS_SECRET` и префиксом `rk-order:`.
3. Строка `body.mac`.
4. Для `Shp_order` — hex от всей строки. В hex только цифры и латинские буквы, поэтому значение безопасно в URL и в подписи Robokassa.

Почему отдельный префикс: токен Robokassa нельзя подставить вместо Mock-подтверждения и наоборот.

### 3.3. Токен-подтверждение

```ts
interface RobokassaReceipt {
  v: 1;
  kind: "rk-receipt";
  id: string;
  inv: string;
  spread: SpreadId;
  amount: number;
  reading: string;
  paidAt: number;
  exp: number;         // paidAt + 30 дней
  method: "card" | "sbp";
  live: 0 | 1;         // боевой или тестовый платёж
}
```

Подпись — HMAC с префиксом `rk-receipt:`.

Флаг `live` обязателен: если на тестовом стенде и на боевом сайте один `PAYMENTS_SECRET`, тестовое подтверждение не должно открывать платную трактовку на боевом сайте.

## 4. Создание платежа

### 4.1. Запрос

`POST /api/payments`

Вход — прежний `ReadingRequest`:

```json
{
  "question": "…",
  "topicId": "love",
  "spreadId": "three",
  "cards": [{ "id": 12, "reversed": false }, "…"]
}
```

Сервер:
1. Проверяет расклад.
2. Берёт сумму из `PRICES`.
3. Создаёт `orderId` и `invId`.
4. Считает отпечаток расклада.
5. Собирает токен заказа.
6. Собирает `Receipt`.
7. Считает подпись Robokassa.
8. Возвращает ссылку на оплату.

### 4.2. Ответ

```json
{
  "orderId": "K7Q3-M9XP",
  "amount": 199,
  "confirmationUrl": "https://auth.robokassa.ru/Merchant/Index.aspx?…",
  "orderToken": "…"
}
```

`orderToken` — тот же токен заказа в hex. Он нужен браузеру, чтобы позже проверить оплату, если уведомление задержится. Токен не секретный: без подписи его не подделать, а чужих данных он не раскрывает.

В режиме `mock` поле `orderToken` можно не возвращать.

### 4.3. Ссылка на оплату

```
https://auth.robokassa.ru/Merchant/Index.aspx
  ?MerchantLogin=nezhnoetaroru
  &OutSum=199.00
  &InvId=179512345678901234
  &Description=Трактовка таро - Разбор ситуации
  &Receipt=<URL-кодированный JSON>
  &Shp_order=<hex-токен>
  &IsTest=1
```

Правила:
- `OutSum` — точка и два знака: `199.00`.
- `Description` — до 100 символов, без кавычек и спецсимволов. Вопрос посетителя не попадает.
- `Receipt` кодируется один раз и в таком же виде участвует в подписи.
- `Shp_order` — hex, без дополнительного кодирования.
- `IsTest=1` только при тестовом режиме.
- `ExpirationDate` — по желанию, в московском времени, формат `YYYY-MM-DDThh:mm`.

### 4.4. Подпись создания

Без чека:

```
MD5(MerchantLogin:OutSum:InvId:Пароль#1:Shp_order=<hex>)
```

С чеком:

```
MD5(MerchantLogin:OutSum:InvId:Receipt:<URL-кодированный JSON>:Пароль#1:Shp_order=<hex>)
```

Порядок важен. Если позже появится холдирование, между `Receipt` и паролем встанет `StepByStep`.

### 4.5. Чек

По умолчанию (`ROBOKASSA_RECEIPT=0`) блок `Receipt` в запрос не передаётся: самозанятый освобождён от 54-ФЗ, а чек НПД регистрирует подключённый сервис «Робочеки СМЗ» через «Мой налог».

Если поддержка скажет передавать чек в Robokassa, включается `ROBOKASSA_RECEIPT=1` и отправляется такой состав:

```json
{
  "items": [
    {
      "name": "Трактовка таро - Разбор ситуации",
      "quantity": 1,
      "sum": 199,
      "payment_method": "full_payment",
      "payment_object": "service",
      "tax": "none"
    }
  ]
}
```

- `tax: "none"` — самозанятая.
- `payment_object: "service"` — услуга.
- `payment_method: "full_payment"` — полная оплата.
- Переключение не требует правки кода: только переменная в Timeweb и перезапуск.

## 5. Result URL — главное уведомление

`GET|POST /api/payments/robokassa/result`

В кабинете настраивается метод **POST**.

### 5.1. Что приходит

```
OutSum=199.000000
InvId=179512345678901234
SignatureValue=…
PaymentMethod=BankCard
Shp_order=<hex>
```

`OutSum` в боевом режиме приходит с шестью знаками после запятой — сравниваем как число, а не как строку.

### 5.2. Проверки по порядку

1. Есть `OutSum`, `InvId`, `SignatureValue`, `Shp_order`.
2. `Shp_order` — валидный токен заказа, `kind=rk-order`, срок `acceptUntil` не истёк.
3. `InvId` из уведомления совпадает с `inv` в токене.
4. Сумма из уведомления совпадает с суммой в токене (допуск 0,005 ₽).
5. Флаг `test` в токене совпадает с текущим режимом.
6. Подпись:

```
MD5(OutSum:InvId:Пароль#2:Shp_order=<hex>)
```

Сравнение — constant-time, без учёта регистра.

Если Robokassa пришлёт подпись без `Shp_order`, разрешаем запасную формулу `MD5(OutSum:InvId:Пароль#2)` и пишем предупреждение. Токен всё равно проверяется отдельно, поэтому подмена заказа невозможна.

### 5.3. Что делает сервер

При успешной проверке:
- записывает в память `invId → { OutSum, PaymentMethod, время }` на 1 час;
- пишет строку в журнал;
- отвечает `OK<InvId>` без перевода строки.

При ошибке:
- пишет причину в журнал;
- отвечает 400, чтобы Robokassa повторила уведомление.

Повторное уведомление:
- ничего не ломает;
- просто обновляет запись в кэше;
- снова отвечает `OK<InvId>`.

Важно: Result URL **не создаёт** подтверждение и **не списывает** деньги. Он подтверждает платёж и наполняет кэш. Это делает повторные уведомления безопасными.

## 6. Success URL — возврат посетителя

`GET /api/payments/robokassa/success`

### 6.1. Проверки

1. Токен `Shp_order` валиден и относится к текущему режиму.
2. Подпись Success URL:

```
MD5(OutSum:InvId:Пароль#1:Shp_order=<hex>)
```

Если Robokassa не включит `Shp_order` в подпись Success URL, допускается запасная формула без него. Токен всё равно проверяется отдельно.

### 6.2. Откуда берётся подтверждение

Порядок:

1. **Кэш Result URL.** Если уведомление уже пришло и сумма совпадает — платёж подтверждён.
2. **`OpStateExt` в боевом режиме.** Если кэша нет, спрашиваем Robokassa:
   ```
   GET https://auth.robokassa.ru/Merchant/WebService/Service.asmx/OpStateExt
     ?MerchantLogin=…
     &InvoiceID=<invId>
     &Signature=MD5(MerchantLogin:InvoiceID:Пароль#2)
   ```
   Платёж считаем успешным только при `Result.Code=0` и `State.Code=100` (деньги зачислены). Код `50` означает «деньги получены, идёт зачисление» — в этом случае подтверждение не выдаём, а возвращаем `pending` и предлагаем проверить через минуту. Так мы не отдаём трактовку, если зачисление в итоге отменится.
3. **Тестовый режим.** `OpStateExt` в тесте не работает, поэтому при `ROBOKASSA_TEST=1` достаточно проверенной подписи Success URL и токена. Денег в тесте нет, риск отсутствует.

Если ни один способ не подтвердил оплату:
- посетитель возвращается на `/?oplata=<orderId>&status=pending`;
- подтверждение не выдаётся;
- на экране оплаты появляется «Проверить оплату».

### 6.3. Что получает посетитель

При подтверждении:

```
/?oplata=K7Q3-M9XP&proof=<HMAC-подтверждение>
```

Дальше работает существующий механизм: `ReadingTable` сохраняет `proof` и запускает трактовку.

При ожидании:

```
/?oplata=K7Q3-M9XP&status=pending
```

При отказе:

```
/?oplata=K7Q3-M9XP&status=failed
```

## 7. Fail URL

`GET /api/payments/robokassa/fail`

- Проверяет только токен заказа.
- Никогда не выдаёт подтверждение.
- Возвращает `/?oplata=<orderId>&status=failed`.
- Если токена нет — на главную.

Fail URL не считается доказательством неуплаты: посетитель мог оплатить, но вернуться не туда. Поэтому на экране отказа остаётся возможность «Проверить оплату».

## 8. Проверка оплаты и восстановление

`POST /api/payments/robokassa/check`

Вход:

```json
{ "order": "<hex-токен>" }
```

Зачем нужно:
- уведомление Robokassa задержалось;
- посетитель закрыл браузер между оплатой и возвратом;
- Success URL не успел подтвердить платёж.

Логика:
1. Проверить токен, срок и режим.
2. В боевом режиме — `OpStateExt`.
3. В тестовом — запись из кэша Result URL.
4. Если оплачено — выдать подтверждение и вернуть:

```json
{ "paid": true, "proof": "…", "orderId": "K7Q3-M9XP", "amount": 199 }
```

5. Если нет:

```json
{ "paid": false, "state": "pending" }
```

Ограничение тестового режима: если посетитель закрыл браузер до Result URL, восстановить платёж в тесте нельзя — Robokassa не даёт проверить тестовую операцию. Это нормально: тестовые деньги ненастоящие.

## 9. Проверка перед трактовкой

`checkPayment()` в `src/lib/payments/server.ts` получает режим:

### 9.1. `mock`

Работает как сейчас: HMAC-подтверждение Mock.

### 9.2. `robokassa`

1. Разбирает `rk-receipt`.
2. Проверяет подпись и срок.
3. Проверяет `live` — тестовое подтверждение не должно работать в боевом режиме.
4. Проверяет `spreadId` и отпечаток расклада.
5. Проверяет, что заказ не в списке возвращённых.
6. Возвращает `PaidOrder` с `held=false`.

Если подтверждение не подходит — 402, как сейчас.

## 10. Одностадийная оплата и тексты

Сейчас в Mock карта «блокируется», а СБП «списывается». В Robokassa на первом запуске обе схемы одностадийные: деньги списываются сразу. Это уже соответствует оферте:

> «Картой. Сумма списывается сразу после успешной оплаты…»
> «Через СБП. Деньги списываются сразу…»

Поэтому:
- `PAY_METHODS.card.hold` становится `false`;
- тексты про блокировку заменяются на «оплата прошла, деньги списаны»;
- `capturePayment` в режиме Robokassa ничего не делает;
- `releasePayment` в режиме Robokassa делает возврат;
- кнопка для карты и СБП называется одинаково — «Вернуть деньги».

Поле `hold` в типах можно оставить на будущее, но в первом запуске оно всегда `false`.

Если позже включим холдирование, придётся обновить оферту: сейчас она обещает списание сразу.

## 11. Возврат

`POST /api/payments/cancel`

### 11.1. Боевой режим

1. Проверить подтверждение.
2. Получить `OpKey` через `OpStateExt`.
3. Собрать JWT:

```json
{
  "OpKey": "…",
  "InvoiceItems": [
    {
      "Name": "Трактовка таро - Разбор ситуации",
      "Quantity": 1,
      "Cost": 199,
      "Tax": "none",
      "PaymentMethod": "full_payment",
      "PaymentObject": "service"
    }
  ]
}
```

4. Подписать HS256 паролем №3.
5. Отправить POST на `https://services.robokassa.ru/RefundService/Refund/Create`.
6. При `success: true`:
   - записать `invId` в список возвращённых на 30 дней;
   - вернуть `{ result: "refunded" }`.

Если `ROBOKASSA_REFUND_RECEIPT=0`, `InvoiceItems` не передаётся — тогда возврат пройдёт без чека возврата. Это временная настройка на случай, если поддержка скажет, что чек аннулируется отдельно.

### 11.2. Тестовый режим

- Реальный возврат не вызывается.
- Сервер пишет в журнал «тестовый возврат» и возвращает `refunded`.
- Нужно только для проверки интерфейса.

### 11.3. Ограничение без базы

Список возвращённых хранится в памяти процесса. Он защищает от повторного открытия трактовки после возврата, пока сервер работает. После перезапуска или на втором экземпляре список теряется.

Для первого запуска это приемлемо. Если возвраты станут частыми, добавим базу отдельным этапом. В документе для владелицы это фиксируется как известное ограничение.

## 12. Маршруты и контракты

| Маршрут | Метод | Назначение | Ответ |
| --- | --- | --- | --- |
| `/api/payments` | POST | создать платёж | `{ orderId, amount, confirmationUrl, orderToken }` |
| `/api/payments/mock` | POST | тестовая оплата | без изменений |
| `/api/payments/robokassa/result` | GET, POST | уведомление Robokassa | `OK<invId>` |
| `/api/payments/robokassa/success` | GET | возврат после оплаты | redirect с `proof` или `status` |
| `/api/payments/robokassa/fail` | GET | возврат после отказа | redirect со `status=failed` |
| `/api/payments/robokassa/check` | POST | проверить оплату | `{ paid, proof?, state? }` |
| `/api/payments/cancel` | POST | возврат | `{ result: "refunded" }` |

Все маршруты:
- `runtime = "nodejs"`;
- `dynamic = "force-dynamic"`;
- `Cache-Control: no-store`;
- не логируют пароли и полные токены.

## 13. Изменения в браузере

### 13.1. `PendingReading`

Добавить:

```ts
orderToken?: string;
```

Токен сохраняется перед уходом на Robokassa. Без него нельзя проверить оплату после закрытия браузера.

Также добавить `orderToken` в `Session` и `sessionRef`, чтобы кнопка «Проверить оплату» работала в текущем раскладе, а не только после перезагрузки страницы.

### 13.2. Возврат со статусом `pending`

Добавить сообщение:

> «Оплата ещё подтверждается. Обычно это занимает несколько секунд. Если деньги уже списались, нажмите „Проверить оплату“ через минуту.»

### 13.3. Кнопка «Проверить оплату»

На экране оплаты, если у заказа есть `orderToken`:
- primary — «Проверить оплату»;
- secondary — «Оплатить заново»;
- пояснение: «Если вы уже оплатили, сначала проверьте оплату — повторное нажатие „Оплатить“ создаст новый заказ».

Это защищает от двойного списания.

### 13.4. Где проверять автоматически

- при возврате со `status=pending`;
- при возврате со `status=failed` (посетитель мог оплатить, но банк вернул не туда);
- при открытии сохранённого оплаченного расклада без `proof`.

Не проверять автоматически при `status=canceled`: человек сам отказался.

## 14. Безопасность — чек-лист

- [ ] Пароли только в переменных окружения Timeweb.
- [ ] Никаких `NEXT_PUBLIC_` для секретов.
- [ ] Подпись Result URL проверяется всегда.
- [ ] Подпись Success URL проверяется всегда.

- [ ] `live` в подтверждении сверяется с режимом.
- [ ] Сравнение подписей — constant-time.
- [ ] `PAYMENTS_SECRET` обязателен в production.
- [ ] Тестовое подтверждение не работает в боевом режиме.
- [ ] Повторное уведомление не создаёт второй платёж и не выдаёт вторую трактовку.
- [ ] Success URL не выдаёт трактовку без Result URL / `OpStateExt` (кроме теста).
- [ ] Возврат не открывает трактовку повторно, пока сервер помнит возврат.
- [ ] В журнал не попадают пароли, номера карт и полные вопросы.

## 18. Известные ограничения первого запуска

1. Нет базы данных: история платежей не хранится на сайте.
2. Список возвратов живёт в памяти и теряется при перезапуске.
3. Холдирование не включено.
4. Тестовый возврат имитируется.
5. Чек НПД формируют «Робочеки СМЗ»; сервис нужно подключить в кабинете. Если он не подключён, чек выдаётся вручную в «Мой налог».
6. `OpStateExt` недоступен в тестовом режиме.
7. При нескольких экземплярах приложения кэш Result URL может не совпасть — тогда сработает `OpStateExt` в боевом режиме.

Все ограничения описаны, ни одно не мешает безопасно принять первый платёж.
