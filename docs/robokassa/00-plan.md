## 0. Короткие ответы на вопросы про личный кабинет

**Что значит «Магазин готов к активации»?**
Это значит, что анкета заполнена достаточно, чтобы отправить магазин на проверку. Кнопка «Запрос на активацию» переводит магазин из тестового состояния в боевое: после одобрения на сайте можно будет принимать настоящие деньги.

**Нажимать ли кнопку сейчас?**
Пока нет. Причина не в кнопке, а в сайте: в кабинете Result URL, Success URL и Fail URL сейчас указывают на главную страницу `https://nezhnoetaro.ru/`. Если активировать магазин сейчас, настоящий платёж будет уходить в никуда: сайт не получит подтверждение оплаты и не выдаст трактовку.

**Можно ли тестировать до активации?**
Да. По документации Robokassa тестовый режим (`IsTest=1` + тестовые пароли) работает и до активации магазина. Настоящие платежи до активации не проводятся.

**Что сделать в кабинете уже сейчас, без кода:**
1. В блоке «Параметры проведения тестовых платежей» выбрать алгоритм расчёта хеша **MD5**. **Сделано 27.11.2026.**
2. Не менять пока Result URL / Success URL / Fail URL на главную. Мы заменим их на реальные адреса после того, как код будет готов и выложен на Timeweb.
3. Пароли №1, №2 и №3 никому не присылать в чат и не вставлять в GitHub. Они понадобятся только в панели Timeweb как защищённые переменные окружения.
4. Пароль №3 — это отдельный пароль для возвратов. Он уже сгенерирован, его не нужно путать с паролем №1 и №2.

**Когда нажимать «Запрос на активацию»?**
После того как:
- код с интеграцией выложен на боевой сайт;
- в кабинете прописаны настоящие Result / Success / Fail URL;
- тестовая оплата прошла весь путь: оплата → подтверждение → трактовка;
- проверены отмена, ошибка и повторная попытка;
- подключены «Робочеки СМЗ» и выбран порядок выдачи чеков НПД.

Точный момент — этап 5 плана.

## 1. Что я меняю в исходном плане

Исходный план в целом верный. Ниже — поправки, которые важны для этого конкретного кода и для Robokassa.

### 1.1. Номер заказа должен быть числом

Сейчас номер заказа — текст вида `K7Q3-M9XP`. Robokassa требует `InvId` — целое число от 1 до 9223372036854775807. Поэтому:
- у заказа появится числовой номер для Robokassa;
- привычный номер для посетителя можно оставить текстовым и передавать его внутри подписанного токена;
- привязка к раскладу (вопрос, тема, карты) останется в подписанном токене и будет передаваться в Robokassa параметром `Shp_order`;
- Robokassa вернёт `Shp_order` обратно в уведомлении, а подпись уведомления будет включать этот параметр.

Это ключевое архитектурное изменение. Без него интеграция не заработает.

### 1.2. Холдирование — не на первом запуске

Холдирование (сначала блокировка суммы, потом списание) в Robokassa:
- работает **только для банковских карт**;
- включается **по отдельному договору** с Robokassa;
- уведомление о предавторизации приходит только на `ResultUrl2`;
- `ResultUrl2` **не отправляется в тестовом режиме**.

Поэтому на первом запуске делаем обычную одностадийную оплату: деньги списываются сразу, а если трактовка не пришла, посетитель может запросить возврат. Это безопасная и проверяемая схема для карт и СБП.

Холдирование добавим отдельным этапом, если Robokassa подтвердит его для самозанятого. Тогда карта сможет работать как сейчас в Mock, а СБП — как обычная оплата с возвратом.

### 1.3. Подтверждение оплаты — только после серверной проверки

Нельзя выдавать трактовку по факту возврата браузера на Success URL. Правильная схема:
1. Robokassa присылает уведомление на Result URL — это главное подтверждение.
2. Сайт проверяет подпись уведомления паролем №2, номер заказа, сумму и подписанный токен расклада.
3. Сайт отвечает Robokassa текстом `OK{InvId}`.
4. Посетитель возвращается на Success URL, и сервер выдаёт подтверждение только после проверки.

Дополнительно в боевом режиме можно перепроверить платёж через `OpStateExt` (пароль №2). Важно: `OpStateExt` не работает в тестовом режиме, поэтому для теста будет отдельная безопасная ветка.

### 1.4. Базы данных по-прежнему нет

Сейчас заказы и подтверждения — подписанные строки, без базы. Это можно сохранить:
- подтверждение оплаты — HMAC-подпись сайта;
- повторные уведомления Robokassa ничего не ломают, потому что проверка не создаёт побочных эффектов;
- возврат делается по номеру заказа через API Robokassa.

Ограничения такого подхода:
- нет списка всех заказов и платежей на сайте;
- нет возможности посмотреть историю в админке;
- при смене `PAYMENTS_SECRET` старые подтверждения перестанут открываться;
- при потере уведомления оплату можно восстановить только через проверку статуса по номеру заказа.

Для первого запуска этого достаточно. Если появятся жалобы или вырастет объём, добавим базу отдельным этапом.

### 1.5. Чеки самозанятого нужно уточнить у Robokassa

В документации Robokassa для своей интеграции требуется передавать состав чека в параметре `Receipt`. Для самозанятого заполняются:
- `tax: "none"`;
- `payment_object: "service"`;
- `payment_method: "full_payment"`.

Но у самозанятых чеки идут через «Робочеки СМЗ». По решению от 27.11.2026 опираемся на документацию: по умолчанию `Receipt` не передаём, чек формирует сервис. Если позже понадобится иначе — включается переменной `ROBOKASSA_RECEIPT=1`, без правки кода.

### 1.6. Параметры Robokassa, которые нельзя менять по ходу

- `OutSum` — сумма с точкой и двумя знаками: `199.00`.
- `Description` — до 100 символов, без спецсимволов. Вопрос посетителя туда не кладём.
- `InvId` — уникальный для каждой попытки оплаты.
- `Result URL` — отвечает `OK{InvId}` и только потом закрывает соединение.
- `Success URL` и `Fail URL` — обычные страницы возврата, не подтверждение оплаты.
- Алгоритм хеша в коде должен совпадать с кабинетом: MD5.

## 3. Переменные окружения (план)

Добавить в Timeweb:

| Переменная | Что это | Секрет |
| --- | --- | --- |
| `PAYMENTS_MODE` | `mock`, `robokassa` или `off` | нет |
| `ROBOKASSA_LOGIN` | `nezhnoetaroru` | нет |
| `ROBOKASSA_TEST` | `1` — тестовые пароли и `IsTest=1`, `0` — боевой режим | нет |
| `ROBOKASSA_TEST_PASSWORD1` | тестовый пароль №1 | да |
| `ROBOKASSA_TEST_PASSWORD2` | тестовый пароль №2 | да |
| `ROBOKASSA_PASSWORD1` | боевой пароль №1 для создания платежа | да |
| `ROBOKASSA_PASSWORD2` | боевой пароль №2 для уведомлений и проверки статуса | да |
| `ROBOKASSA_PASSWORD3` | боевой пароль №3 для возвратов | да |
| `ROBOKASSA_RECEIPT` | `1` — передавать чек в Robokassa | нет |
| `ROBOKASSA_REFUND_RECEIPT` | `1` — передавать состав чека при возврате | нет |
| `PAYMENTS_SECRET` | секрет подписи подтверждений сайта | да |

Правила:
- никаких `NEXT_PUBLIC_` для паролей;
- пароли не попадают в GitHub;
- при смене `PAYMENTS_SECRET` старые подтверждения перестают работать — менять только осознанно.

## 4. Главные риски

| Риск | Как снижаем |
| --- | --- |
| Активировали магазин до готовности сайта | Не нажимаем до этапа 5; URL пока не меняем на боевые |
| Трактовка выдана без денег | Подтверждение только после проверки подписи Result URL / `OpStateExt` |
| Одна оплата открывает другой расклад | В подтверждении остаётся отпечаток вопроса, темы и карт |
| Повторное уведомление ломает заказ | Обработка без побочных эффектов, подтверждение детерминировано |
| Потерялось уведомление | Кнопка «Проверить оплату» через `OpStateExt` в боевом режиме |
| Тестовые пароли попали в боевой режим | Отдельный флаг `ROBOKASSA_TEST`, проверка при старте |
| Самозанятый возврат оформлен неправильно | Уточняем у поддержки, возврат через API + аннулирование чека |
| Нет базы и истории платежей | Пока принимаем; при росте — отдельный этап с БД |
