## 1. Коротко

Сейчас на сайте работает **тестовая оплата**. Она полностью имитирует путь посетителя, но:
- вместо Robokassa открывается страница `/oplata`;
- «оплата» подтверждается нажатием кнопки;
- `capturePayment` и `releasePayment` только пишут строку в журнал сервера;
- ни одно реальное списание, блокировка или возврат не выполняются.

Хорошая новость: архитектура уже разделяет «создать платёж», «проверить оплату», «списать» и «вернуть». Это позволяет добавить Robokassa, не переписывая сайт заново.

Плохая новость: текущий номер заказа — текст, а Robokassa требует числовой `InvId`. Кроме того, нынешнее «подтверждение оплаты» создаётся тестовой страницей, а не банком. Эти две вещи придётся заменить, но интерфейс посетителя можно сохранить почти без изменений.

## 2. Схема текущего процесса

```
Посетитель выбирает расклад
        │
        ▼
ReadingTable: карты легли, цена > 0
        │  POST /api/payments
        │  { question, topicId, spreadId, cards }
        ▼
createPayment()
  - сумма из PRICES (не из браузера)
  - orderId = "K7Q3-M9XP"
  - HMAC-токен заказа: id, spreadId, amount,
    fingerprint(вопрос + тема + карты), exp = 1 час
  - confirmationUrl = /oplata?zakaz=<токен>
        │
        ▼
Браузер сохраняет заказ в localStorage
и уходит на /oplata
        │
        ▼
MockCheckout: выбор СБП/карты, «Оплатить»
        │  POST /api/payments/mock { zakaz, method }
        ▼
confirmMockPayment()
  - проверяет HMAC и срок
  - создаёт HMAC-подтверждение (receipt), exp = 30 дней
  - пишет в журнал «деньги получены/заблокированы»
        │
        ▼
возврат на /?oplata=<id>&proof=<receipt>
        │
        ▼
ReadingTable сохраняет proof в localStorage
        │  POST /api/reading { ..., payment: proof }
        ▼
checkPayment()
  - проверяет HMAC
  - сверяет spreadId и fingerprint расклада
  - отдаёт PaidOrder
        │
        ▼
Трактовка пишется потоком.
Если карта (held=true) и трактовка готова — capturePayment() (только лог).
Если трактовка не пришла — releasePayment() (только лог).
```

## 4. Текущие контракты

### 4.1. Заказ

```ts
interface Order {
  id: string;        // "K7Q3-M9XP"
  spreadId: SpreadId;
  amount: number;    // рубли, целое
}
```

Внутри подписанного токена дополнительно:
- `kind: "order" | "receipt"`;
- `reading` — SHA-256 отпечаток `[spreadId, topicId, question, cards]`, 22 символа;
- `exp` — срок;
- `method` — способ оплаты у подтверждения.

Сроки:
- ссылка на оплату — 1 час;
- подтверждение оплаты — 30 дней.

### 4.2. API

`POST /api/payments`
- вход: `ReadingRequest`;
- выход: `{ orderId, amount, confirmationUrl }`;
- сумма берётся из `PRICES`;
- если цена 0 — 400.

`POST /api/payments/mock`
- работает только при `PAYMENTS_MODE=mock`;
- вход: `{ zakaz, method }`;
- выход: `{ orderId, returnUrl }`.

`POST /api/payments/cancel`
- вход: `{ proof }`;
- выход: `{ orderId, amount, result: "canceled" | "refunded" }`;
- сейчас только лог.

`POST /api/reading`
- вход: `ReadingRequest + payment?: proof`;
- без оплаты платного расклада — 402 `payment_required`;
- с корректным proof — трактовка и события `payment`.

### 4.3. События оплаты в потоке трактовки

```ts
{ type: "payment", status: "held" | "paid" | "captured", orderId, amount }
```

`held` — сумма заблокирована; `paid` — деньги получены; `captured` — трактовка готова, блокировка списана.

## 5. Что важно сохранить

1. **Сумму назначает только сервер.** `PRICES` — единственный источник цены.
2. **Оплата привязана к раскладу.** Отпечаток вопроса, темы и карт не даёт открыть другой расклад.
3. **Платная трактовка не выдаётся без подтверждения.** Проверка стоит до запуска генерации.
4. **Бесплатный расклад и лимиты.** `FREE_SPREAD`, `FREE_PER_DAY`, `FREE_PER_IP_PER_DAY` работают независимо от платёжного режима.
5. **Возврат к раскладу после оплаты.** Заказ хранится в localStorage, поэтому карты не теряются.
6. **Повтор трактовки по той же оплате.** Если ИИ не ответил, подтверждение остаётся действительным.
7. **Понятные сообщения об отмене, ошибке и повторной попытке.**
8. **Mock-режим.** Должен остаться рабочим для разработки.

## 6. Находки и риски

| № | Находка | Влияние | Решение |
| --- | --- | --- | --- |
| 1 | `orderId` — текст `K7Q3-M9XP`, а Robokassa требует числовой `InvId` | Интеграция не заработает без числового номера | Добавить числовой `InvId`; текстовый номер оставить для посетителя |
| 2 | Привязка к раскладу хранится только в HMAC-токене на сайте | Robokassa не знает о раскладе | Передавать подписанный токен в `Shp_order` и проверять его в уведомлении |
| 3 | `PAYMENTS_MODE` знает только `off` и `mock`; неизвестное значение молча становится `mock` | Опечатка `robokassa` тихо включит тестовую оплату | Добавить явный режим и громкую ошибку при неизвестном значении |
| 4 | `confirmMockPayment` создаёт подтверждение без банка | В боевом режиме так нельзя | В Robokassa подтверждение создаётся только после Result URL / проверки статуса |
| 5 | `capturePayment` и `releasePayment` только пишут лог | Нет реального списания и возврата | Одностадийная оплата: capture не нужен; возврат — через Refund API |
| 6 | Нет базы данных | Нет истории платежей и админки | Пока оставить stateless; при росте — БД |
| 7 | Срок заказа 1 час, а уведомление может прийти позже | Оплата на последней минуте может не открыть трактовку | Разделить «срок ссылки» и «срок принятия уведомления» |
| 8 | `OutSum` в боевом Result URL приходит с 6 знаками после запятой | Сравнение строк сломается | Сравнивать как число с допуском |
| 9 | `ResultUrl2` не отправляется в тестовом режиме | Холдирование нельзя проверить на тесте | Холдирование — отдельный этап после запуска |
| 10 | Возврат требует `Password3` и `OpKey` | Без них возврат невозможен | `Password3` уже есть; `OpKey` получать через `OpStateExt` в боевом режиме |
| 11 | `OpStateExt` не работает в тестовом режиме | Нельзя проверить статус тестового платежа | Для теста — Result URL; для боевого — `OpStateExt` |
| 12 | В кабинете тестовый алгоритм хеша не выбран | Тестовая подпись не сойдётся | Выбрать MD5 вручную |
| 13 | Result/Success/Fail URL указывают на главную | После активации платежи не будут подтверждаться | Заменить на API-маршруты до активации |
| 14 | Нет реального теста подписей | Ошибка в порядке параметров обнаружится на деньгах | Вынести подписи в чистые функции и покрыть тестами |
| 15 | `paymentsInfo().test` — единственный признак теста в UI | В боевом режиме может остаться надпись «тестовая оплата» | Расширить информацию о режиме |

## 7. Чего в текущем коде нет и что придётся добавить

1. Формирование ссылки на Robokassa с MD5-подписью.
2. Проверку `SignatureValue` в Result URL паролем №2.
3. Проверку `SignatureValue` в Success URL паролем №1 (для тестовой ветки).
4. Числовой `InvId` и передачу `Shp_order`.
5. Проверку суммы с учётом шести знаков после запятой.
6. Ответ `OK{InvId}` в формате, который ждёт Robokassa.
7. Реальный возврат через `https://services.robokassa.ru/RefundService/Refund/Create`.
8. Проверку статуса через `OpStateExt` для восстановления потерянных уведомлений.
9. Передачу `Receipt` для чека самозанятого (после уточнения у поддержки).
10. Защиту от запуска боевого режима с тестовыми паролями.

## 8. Что можно не менять

- `ReadingTable` уже умеет: сохранить заказ, уйти на внешний адрес, вернуться по `?oplata=...&proof=...`, показать отмену/ошибку, повторить трактовку, запросить возврат.
- `client.ts` уже хранит ожидающие расклады и бесплатный лимит.
- `reading` уже проверяет оплату до генерации и умеет повтор.
- `MockCheckout` и `/oplata` можно оставить как есть для режима `mock`.

## 9. Вопросы, которые нужно закрыть до кода

1. **Холдирование.** Доступно ли самозанятому? Если да — на каких условиях? Пока считаем, что нет.
2. **Чеки.** Нужно ли передавать `Receipt` в запросе или «Робочеки СМЗ» формируют чек автоматически по настройкам кабинета?
3. **Возврат.** Достаточно ли Refund API, или для самозанятого нужно отдельно аннулировать чек в «Мой налог»?
4. **Активация.** Какие страницы проверяет модерация? Оферта, политика, контакты и условия возврата на сайте уже есть — нужно убедиться, что они доступны без JS и с главной.
5. **Тестовый платёж.** Какая тестовая карта актуальна и есть ли ограничения по сумме?
